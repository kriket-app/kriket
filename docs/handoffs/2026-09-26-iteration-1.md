## Product feedback so far, to design iteration 2 around

- Erik, after the tour: the app "feels like just a spreadsheet". Expected from items 0 to 3, but iteration 2 has
  to think much harder about market fit, real usability for real people with real habits, and solving a holistic
  problem, not adding rows.
- The pitch-feedback recording (day 1, private transcript in the handoff folder) said, in substance: the
  differentiator over a spreadsheet is how low-lift the data entry is (statement upload, or read-only bank access
  that compiles what you spend and when, versus punching everything in); people either give an app everything or
  refuse to type, and that balance is the hard part; the persona is the young person with variable income who
  does not track anything today, not the receipt-logging enthusiast; security and trust matter as much as
  features; and the three concepts (income streams, expense streams, goals) are simple enough to understand, so
  keep them.
- Open questions from Erik: does Tags need its own page at all; the all-green tag palette is limiting.
- From testing the live app (Erik and Theo, day 1 afternoon; more was still coming, so this list is
  incomplete on purpose):
  1. Logged in, tried to add a balance: the Save button did nothing visible. Even if it saved, there is no
     way of knowing it worked.
  2. On the add income and add expense screens the date picker is the browser's default, not shadcn's; it
     breaks the styling.
  3. If only the usual amount is entered, minimum and maximum should equal it. Don't make people fill out
     all three.
  4. Too many presets are shown; reduce them, and let the user change a tag's colour. The tag screen might
     or might not be useful.
- Hold off on planning iteration 2 until the founders say the feedback is complete.

## The working style that worked (keep)

1. **Contract first, then parallel builds.** A short plan with the spec, the constraints, and the exact API contract
   let a backend agent and a frontend agent build at the same time and meet in the middle. Write the contract before
   dispatching anything.
2. **Fresh reviewer per task, then one whole-branch review on the strongest model, then one fix wave and one scoped
   re-review.** The whole-branch review found the three things that mattered (a broken local setup path, a
   proxy-trust bug that would have rate-limited all visitors as one, and "today" being UTC). Task reviews on the mid
   tier, implementers on the mid tier when the plan carries the code and on the strong tier for design work.
3. **Rulings in a ledger, reported back.** Every decision made on the founders' behalf went into the ledger as
   "Ruling: what, why, cost if wrong" and was listed in the final report. Keep doing that; it is how the humans undo
   a wrong call.
4. **Living pages instead of status messages.** The board, the tour, and the index gave both founders one place to
   look; the tour's real screenshots are what produced the product feedback. Republish at milestones; archive each
   tour iteration.
5. **PRs: every callout in the description, nobody tagged, opened ready for review; merge by hand when green.** Erik's
   standing rule, and after the auto-merge mistake, the only way.
6. **Erik answers in prose.** Offer options and a recommendation in the message, end with one open decision, never a
   menu prompt.
7. **Verify on the real thing.** The first real sign-up through the public URL was the one path no test covered; do
   it after every deploy.

## Improvements for next time

1. **Do the discovery before the plan.** Iteration 1 went straight from whiteboard to contract. Iteration 2 needs
   a short product step first: the persona, the low-lift entry story, what "not a spreadsheet" means on screen,
   with Theo's notes and the pitch feedback as inputs; then the contract.
2. **Protect `main` before the first PR**, not after. Auto-merge on an unprotected branch merges at once.
3. **Run CI on the real repo early.** Three failures appeared only on the organisation repo's runners (a licensed
   action, generated files out of date, a database race). Push a trivial PR first and watch it go green.
4. **Match the local Node to the pin.** Node 26 is pinned; local runs used Node 24 with the engine check relaxed.
   Install Node 26 (`nvm install 26`) at the start of the next session.
5. **Read the clock, don't estimate it.** Board timestamps drifted twice; take times from `date` and from GitHub.
6. **One agent per directory when running in parallel, and stage by path.** A shared index swept one agent's
   deletions into another's commit; harmless, but stage explicitly.
7. **Smaller iteration-2 tasks with a demo checkpoint each**, so the founders can steer between them instead of
   after a four-task batch.
8. **Keep the tour kit and the page tools in the repo** (done in this handoff) so refreshing them is a re-run, and
   note that the site's hand-published paths (`/kriket/`, `/board/`, `/tour/`) live outside the kit site's generated
   build.
